# Wabi-Sabi (侘寂)

## หลักการ
Wabi-Sabi — "ความงามในความไม่สมบูรณ์และความไม่คงทน" — คือการยอมรับว่าไม่มีสิ่งใด
สมบูรณ์ ถาวร หรือเสร็จสมบูรณ์ มีศักดิ์ศรีในสิ่งที่ไม่สมบูรณ์และในช่วงเวลาที่ผ่านไป
ความไม่สมบูรณ์ไม่ใช่ความล้มเหลว แต่คือสภาพธรรมชาติ

## ในการพัฒนา Software
Code ที่สมบูรณ์แบบไม่ได้ถูก ship Code ที่ใช้ได้แต่ไม่สมบูรณ์แบบให้บริการ user ได้
เป้าหมายไม่ใช่ความสมบูรณ์แบบ แต่คือความเหมาะสมกับจุดประสงค์ พร้อมยอมรับข้อจำกัดอย่างตรงไปตรงมา

- MVP ที่ทำงานได้มีคุณค่ากว่าการออกแบบที่สมบูรณ์แบบที่ไม่มีอยู่จริง
- Tech debt ไม่ใช่ความล้มเหลว — มันคือการแลกเปลี่ยนอย่างมีสติ ตั้งชื่อมัน ติดตามมัน ชำระคืน
- ระบบไม่มีวันเสร็จสมบูรณ์ มันวิวัฒนาการ ออกแบบให้รับการเปลี่ยนแปลง ไม่ใช่ให้คงทนตลอดกาล
- ยอมรับว่า code ที่เขียนเมื่อปีที่แล้วดูมีข้อบกพร่องในสายตาวันนี้ — นั่นคือการเติบโต
- ข้อจำกัดสร้างความคิดสร้างสรรค์ สภาพที่ไม่สมบูรณ์คือที่ที่ solutions จริงๆ เกิดขึ้น

## คำถามนำทาง
- สิ่งนี้ดีพอที่จะ ship และให้บริการ user ได้ตอนนี้เลยไหม?
- เรายอมรับอะไรเป็นการแลกเปลี่ยนอย่างมีสติ และ document ไว้แล้วไหม?
- กำลังไล่ตามความสมบูรณ์แบบโดยแลกกับการส่งมอบคุณค่าอยู่ไหม?
- อะไรที่ต้องเปลี่ยนแปลงอย่างหลีกเลี่ยงไม่ได้ และทำให้มันง่ายขึ้นแล้วไหม?
- ซื่อสัตย์เกี่ยวกับข้อจำกัดของแนวทางนี้ไหม?

## Anti-patterns ที่ควรหลีกเลี่ยง
- บล็อก release เพราะ code "ยังไม่สมบูรณ์แบบ"
- แกล้งทำเป็นว่า tech debt ไม่มีอยู่หรือไม่สะสม
- Over-engineer เพื่อ scale สมมุติที่อาจไม่มีวันมาถึง
- Rewrite ระบบแทนที่จะค่อยๆ ปรับปรุงมัน
- มอง design ปัจจุบันว่าถาวร
