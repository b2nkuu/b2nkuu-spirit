# Kaizen (改善)

## หลักการ
Kaizen — "เปลี่ยนเพื่อดีขึ้น" — คือปรัชญาของการพัฒนาอย่างต่อเนื่องทีละก้าว
ไม่ใช่การก้าวกระโดดครั้งใหญ่ แต่คือความก้าวหน้าที่สม่ำเสมอสะสมทุกวัน

## ในการพัฒนา Software
อย่ารอ "sprint refactor ใหญ่" ที่ไม่มีวันมาถึง ปรับปรุงเล็กน้อยทุกครั้งที่แตะ code
ทุก PR คือโอกาสทิ้ง codebase ให้ดีกว่าตอนที่รับมา

- เลือกการปรับปรุงเล็กๆ ที่ปลอดภัยแทน rewrite ครั้งใหญ่
- เวลาที่ดีที่สุดในการ refactor คือตอนที่อยู่ใน code นั้นอยู่แล้ว
- การปรับปรุงสะสม — 1% ดีขึ้นทุกวัน เปลี่ยน codebase ได้อย่างมากในรอบปี
- วัดความก้าวหน้า: benchmarks, test coverage, error rates, build times

## คำถามนำทาง
- มีสิ่งเล็กๆ อะไรที่ปรับปรุง code นี้ได้ตอนนี้เลย?
- PR นี้ทิ้ง codebase ไว้ดีกว่าตอนรับมาไหม?
- การเปลี่ยนแปลงเล็กที่สุดอะไรที่ลด friction ให้ developer คนต่อไป?
- metric อะไรที่บอกได้ว่าสิ่งต่างๆ ดีขึ้นหรือแย่ลง?
- ทำให้เข้าใจง่ายขึ้นหรือยากขึ้นกว่าตอนมาถึง?

## Anti-patterns ที่ควรหลีกเลี่ยง
- "เดี๋ยวค่อยมาจัดการ" โดยไม่มีแผนหรือ ticket ที่ชัดเจน
- Rewrite ขนาดใหญ่ที่ไม่มี checkpoint ทีละขั้น
- มองการปรับปรุงเป็น phase แยก แทนที่จะเป็น habit ต่อเนื่อง
- มองข้ามปัญหาเล็กๆ เพราะคิดว่าไม่สำคัญ
- Ship code ที่เข้าใจยากกว่าสิ่งที่มันมาแทน
